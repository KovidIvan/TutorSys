# TutorSys: следующие шаги для агента

## Текущее состояние
Проект запускается: 31 тест проходит на Django 5.2, миграции применяются, `seed.run()` отрабатывает, `runserver` стартует (проверено пользователем на SQLite).
Не подтверждено: ручной сценарий в браузере и работа на PostgreSQL.

## Ограничения
- Архитектуру не расширять: без новых приложений, моделей и миграций, без смены стека.
- Правки точечные. Не переписывать работающий код ради стиля.
- Не коммитить `.env`, `db.sqlite3`, `.venv/`, `env/`.
- Перед каждым коммитом запускать `python manage.py test core`; все 31 тест должны проходить.
- Если что-то неоднозначно, выбрать более простой вариант, записать допущение и продолжить.

## Шаг 1. Новая ветка
Все изменения ниже делать в отдельной ветке от текущего состояния:
```
git switch -c polish-demo
```

## Шаг 2. Быстрые правки
1. **Flash-сообщение при HTMX** (`core/views.py`, `distribution_view`): `messages.success(request, 'Назначение обновлено.')` вызывается и для HTMX-запроса, но partial `_teacher_panel.html` его не выводит, поэтому сообщение всплывает на следующей странице. Перенести вызов в ветку без HTMX (после блока `if request.htmx: return render(...)`, перед `redirect`). Тест `test_htmx_assignment_returns_updated_teacher_panel` должен остаться зелёным; добавить в него проверку, что при HTMX-запросе сообщений в сессии не накапливается.
2. **Переводы строк**: добавить в корень `.gitattributes`:
   ```
   * text=auto
   *.py text eol=lf
   *.html text eol=lf
   *.md text eol=lf
   ```
   Затем `git add --renormalize .`. После этого `git status` не должен показывать файлы, изменённые только окончаниями строк.
3. **Служебные файлы**: `TutorSys_agent_report.md`, `TutorSys_agent_tasks.md`, `TutorSys_next_steps.md` перенести в папку `docs/agent/` и закоммитить (или удалить, если пользователь скажет).

## Шаг 3. Улучшения демо (по порядку, останавливаться при нехватке времени)
1. **Меньше жёлтых предупреждений в демо.** Сейчас почти у всех преподавателей предупреждение «меньше минимума» и «лекций меньше нормы», потому что демо-нагрузка намного меньше годовой нормы. Варианты, выбрать самый простой:
   - в `seed.py` задать демо-должностям пониженные `min_hours` и `min_lecture_hours`, при этом не трогая логику `check_teacher`;
   - либо ничего не менять и описать это в README в разделе демо.
   Контрольный тест 277.95 ч и тесты на `check_teacher` не менять: они создают свои данные.
2. **Привязка нагрузки к демо-преподавателю.** Убедиться, что после `seed.run()` и пересчёта у пользователя `teacher` (Мария Петрова) есть что выбрать в журнале. Если нет, добавить в раздел демо README явный шаг: «`head` назначает Марии Петровой хотя бы один элемент нагрузки». Не создавать нагрузку автоматически в seed без необходимости.
3. **README**: полностью переоформить по требованиям из шага 3а.

## Шаг 3а. Оформление README.md
Переписать `README.md` как аккуратную витрину проекта. Содержимое брать из фактического кода, ничего не выдумывать; все команды проверить на реальном запуске. Язык русский, команды для PowerShell (в скобках добавить эквивалент для bash, если он отличается).

Структура, в этом порядке:
1. **Заголовок и краткое описание**: одно предложение, что делает система, и 3–5 пунктов основных возможностей (расчёт нагрузки по нормам, распределение между преподавателями с HTMX, журнал занятий, отчёт план/факт, экспорт в Excel).
2. **Стек**: Django 5, HTMX, Bootstrap 5, openpyxl, SQLite или PostgreSQL.
3. **Роли и доступ**: таблица «роль, что может, основные страницы».
4. **Быстрый старт**: пронумерованные шаги от клонирования до `runserver` в блоках кода (venv, зависимости, `.env`, миграции, seed, запуск). Отдельно: как переключиться на PostgreSQL.
5. **Демо-учётные записи**: таблица `deputy_dean`, `head`, `teacher` (пароль `pass123`), отметка, что пароли только для демо. Одной строкой про остальных семь пользователей (без пароля и ролей) и про `createsuperuser` для `/admin/`.
6. **Сценарий демо на 3–5 минут**: нумерованный список по ролям с ожидаемым результатом каждого шага.
7. **Как считается нагрузка**: короткая таблица «вид работы, как считается», с опорой на `core/calculations.py` и `CalcSettings` (лекции на поток, практики на группу, лабораторные на подгруппу, экзамен вместе с консультацией, зачёт, УСР, контрольные работы).
8. **Принятые допущения**: экзамен и консультация в одном элементе; план отчёта распределяется на 5 месяцев семестра (сентябрь–январь и февраль–июнь, июль и август равны нулю); в демо много предупреждений «меньше минимума» из-за малой демо-нагрузки.
9. **Структура проекта**: дерево каталогов с однострочными пояснениями (`nagruzka/`, `core/models.py`, `calculations.py`, `views.py`, `seed.py`, `templates/`, `static/core/vendor/`).
10. **Тесты**: команда запуска и ожидаемый результат (31 тест).
11. **Известные ограничения**: проверено на SQLite (PostgreSQL указать, только если реально проверен), `seed.run()` очищает данные кроме пользователей, демо-пароли не для production.

Требования к оформлению:
- Один заголовок первого уровня, дальше `##` и `###` без пропусков уровней.
- Команды только в блоках кода с указанием языка (` ```powershell `, ` ```dotenv `), без смешивания команд и пояснений в одной строке.
- Таблицы для ролей, учётных записей и видов нагрузки; списки для шагов. Без эмодзи и декоративных баннеров.
- Длина разумная: без повторов того, что есть в `SETUP_INSTRUCTIONS.txt` и `SEED_INSTRUCTIONS.txt`. Эти файлы либо удалить, либо заменить в них содержимое одной строкой «см. README.md» и сообщить об этом в отчёте.
- Все пути, URL и имена команд сверить с кодом (`core/urls.py`, `nagruzka/urls.py`, `core/seed.py`).

## Шаг 4. Проверка PostgreSQL (если он нужен для сдачи)
1. Создать пустую БД `nagruzka`, заполнить в `.env` `DB_ENGINE=django.db.backends.postgresql`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`.
2. Выполнить `python manage.py migrate`, `seed.run()`, `python manage.py test core` (Django создаст тестовую БД, у пользователя нужны права `CREATEDB`).
3. Если есть расхождения с SQLite (регистр, `Decimal`, сортировка), исправить точечно и описать в README.
4. Если PostgreSQL недоступен, не изображать проверку: записать в README, что проверено только на SQLite.

## Шаг 5. Ручной сценарий (обязателен перед сдачей)
Выполнить по README и зафиксировать результат в отчёте:
1. `deputy_dean`: «Параметры» → «Пересчитать нагрузку всех кафедр».
2. `head`: «Распределение» → выбрать преподавателя у элемента нагрузки. Правая панель должна обновиться без перезагрузки страницы; при превышении максимума бейдж «critical».
3. `teacher`: «Моя нагрузка», добавить запись в журнал на назначенный элемент, открыть отчёт план/факт.
4. Excel: у `head` скачать «Нагрузка» и «Преподаватели», у `teacher` скачать нагрузку, журнал и отчёт. Каждый файл должен открываться без ошибок.
5. Проверка прав: `teacher` открывает `/settings/` и `/distribution/` → страница 403 с `error.html`; `head` не может назначить элемент другой кафедры.
Найденные дефекты исправить, добавив регрессионный тест; новый функционал не добавлять.
